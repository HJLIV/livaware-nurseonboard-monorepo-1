# Livaware NurseOnboard

Full-stack TypeScript monorepo (Express 5 + React/Vite + PostgreSQL/Drizzle) combining **Clinical-Skills-Arcade**, **Nurse-Preboard**, and **Nurse-Onboard**. Deployed on Replit autoscale.

## Run

- `npm run dev` — Express on :5000 (serves Vite)
- `npm run build` / `npm start` (prod = `node dist/index.cjs`)
- `npm run db:push` — Drizzle schema push
- `npm test` — Vitest API tests (outbound email is suppressed in test mode via `isEmailSendingSuppressed()` in `server/outlook.ts`; `tests/setup.ts` auto-cleans created test nurses/candidates per file)

## Architecture

- **Frontend**: `client/` — React 18, Tailwind, Radix/shadcn, Framer Motion, Recharts, RHF + Zod
- **Backend**: `server/` — Express 5, express-session, MSAL SSO, Microsoft Graph, OpenAI/Anthropic
- **Shared schema**: `shared/schema.ts` — Drizzle + Zod. FK column is `nurseId` everywhere. Compatibility aliases: `candidates → nurses`, `magicLinks → portalLinks`, `users → arcadeUsers`, `modules → arcadeModules`, `assessments → preboardAssessments`.
- **Stage terminology**: DB enum (`preboard | onboard | skills_arcade | completed`) is unchanged; UI shows display names **Applicant / Candidate / Skills Arcade / Nurse** via `STAGE_DISPLAY_NAMES`.

## Modules

- **Nurse-Onboard** (`server/routes/onboard.ts`, `portal.ts`, `referee.ts`) — AI compliance/NMC/DBS/references/certificates/passport/health-triage, Outlook + SharePoint, magic-link portal.
- **Skills Arcade** (`server/routes/skills-arcade.ts`) — 40 seeded scenarios, scoring, trainer remediation, admin reports. Platform admins bridge in via `isPlatformAdmin()`. **Auto-enrolment**: a newly-provisioned nurse arcade account is immediately enrolled in every current module (`enrolUserInAllModules` helper, idempotent skip-if-exists, "not started" status) via `ensureArcadeUserForNurse` (best-effort — never fails account creation; pass `{autoEnrol:false}` when the caller owns counting). Super-admin backfill `POST /api/admin/enrol-all` (default no emails, opt-in `{notify:true}`) iterates all platform nurses, ensures each arcade user, enrols missing modules, returns `{nursesProcessed, enrolmentsCreated, skippedNurseIds, emailsSent}`. **Per-nurse failures are isolated** (each loop iteration is try/caught → logged + pushed to `skippedNurseIds` + `continue`) so one bad record can never 500 the whole backfill; `ensureArcadeUserForNurse` returns `null` (skip) on a missing email and falls back to `getUserByUsername` before `createUser` to dodge the `arcade_users.username` UNIQUE constraint when two nurses share an email. "Enrol All Nurses" button on `/arcade/admin/modules`. Manual "Assign to Nurses" flow unchanged. Audits via existing `skills_arcade`/`assign_module` taxonomy (`detail.auto:true`, `reason: arcade_account_created | enrol_all_backfill | enrol_all_backfill_run`).
- **Preboard** (`server/routes/preboard.ts`) — Timed AI assessment, PDF + email.
- **Onboarding access gate** (`server/services/onboarding-gate.ts`, middleware `requireOnboardingUnlocked`) — Onboarding/Compliance/Arcade locked until 3 prerequisites (preboard examination, ≥1 competency declaration, admin CV-review). Per-nurse `onboardingUnlockMode` (`auto`/`manual`). Locked portal writes return `403 { error: "onboarding_locked", gate }`.
- **Grace early-access** (per-nurse) — `nurses.graceAccessEnabled` (+ `graceAccessUpdatedAt/By`) lets an admin open the **whole Training section** (Mandatory Training, Internal Training, Clinical Skills Arcade), **Invoicing** and **Availability** for an individual nurse *before* compliance approval, induction completion and the `completed` stage are reached. It does **not** bypass the Assessment gate (`requireOnboardingUnlocked` is untouched). Surfaced in `GateState.graceAccess` (`gateStateFromNurse`). Backend bypasses: `requireInductionAcknowledged` (`server/middleware.ts`) short-circuits when the flag is set; invoices `requireCompletedStageRead/Write` and availability `ensureCompletedNurse` allow `currentStage === "completed" || graceAccessEnabled`. Admin toggle: `PUT /api/nurses/:id/grace-access` (`requireAdmin`, body `{enabled}`, idempotent, audit `admin` / `grace_access_granted` | `grace_access_revoked`), returns the gate state. FE: `OnboardingAccessPanel` Switch (`/nurses/:id` → onboarding-access card); `portal-shell.tsx buildPortalGroups` opens Training when `gate.graceAccess`; portal pages (`portal-hub`, `section`, `internal-training`, `invoices`, `availability`) treat `gate.graceAccess === true` like `completed` for Availability/Invoices visibility.
- **Individual Agreements** (`server/routes/individual-agreements.ts`, `server/agreements/storage.ts` + `pdf.ts`) — ad-hoc, admin-issued agreements per nurse for a **project / patient / deployment / other** (task 191). Admin uploads the agreement document (PDF/DOCX → normal `documents` row, type `individual_agreement`) from the nurse-detail "Individual Agreements" tab (`client/src/components/admin/individual-agreements-panel.tsx`). Table `nurseAgreements` (`shared/schema.ts`, enums `nurse_agreement_status` pending/signed/voided + `nurse_agreement_context`). On create/replace the document's text is extracted to Markdown (`extractPolicyFromFile` reuse; `nurseAgreements.contentMarkdown` / `extractionError`, task 195) so the nurse reads it **in-app** with the design-system renderer (`PolicyBody`) behind a scroll-to-end gate; extraction failure falls back to the old PDF iframe / DOCX download. Issuing also fires a fire-and-forget email to the nurse (`sendIndividualAgreementIssuedEmail`, template `individual_agreement_issued`, minted 30-day portal link; audit `individual_agreement_email_sent`; mail failure never blocks creation). Nurse signs in the portal (`client/src/pages/portal/agreements.tsx`, routes `/portal/agreements` + legacy `/:token`) with the Service-Agreement ceremony: explicit read-confirmation checkbox, typed legal name; IP/UA captured; **sealed** signed PDF rendered **before** the signature is recorded (never signed-but-PDF-less) and stored as a `documents` row (type `individual_agreement_signed`, mirrored to object storage). The sealed PDF (`server/agreements/pdf.ts` + shared helpers in `seal.ts`, task 201) contains the full agreement wording — `contentMarkdown` rendered by the reusable Markdown→pdfkit renderer `server/pdf/markdown-pdf.ts` (headings, lists, quotes, rules, code, GFM tables, inline bold/italic/code/links) — followed by an Execution block (typed signature, timestamp, IP, device, issuer) and the original document's name + SHA-256 fingerprint; it is written with a random owner password so readers treat it as non-modifiable. When the wording could not be extracted the PDF says so explicitly and certifies the separately-held original. Both the portal card and the admin panel offer the sealed PDF as the primary download with the original upload secondary. Legacy records signed before this can be rebuilt from the signature already on record — `POST /api/agreements/regenerate-signed-pdfs` (admin; optional `agreementIds`, `server/agreements/regenerate.ts`) re-extracts missing wording, relinks the new document, deletes the superseded one, isolates per-agreement failures, and audits `individual_agreement_pdf_regenerated`; the admin panel exposes it per agreement as "Rebuild signed PDF". Portal endpoints `GET /api/portal/:token/agreements` + `POST .../:id/sign` (`validatePortalToken` only — intentionally **not** compliance/onboarding gated: the admin's act of issuing is the gate; double-sign → 409; voided hidden from the nurse). Admin endpoints `GET/POST /api/nurses/:id/agreements`, `POST /api/agreements/:id/void` and `.../replace-document` (pending only; signed rows are immutable). Portal summary (`GET /api/portal/:token`) includes an `agreements {total, outstanding}` block; sidebar shows "Individual agreements" in the Induction group only when at least one exists (every portal page passes `agreementsSummary` into `buildPortalGroups`, and the portal-hub home shows a "Signature required" card while any are outstanding). Audit module `service_agreement` (actions `individual_agreement_created/signed/voided/document_replaced/pdf_generated`). Tests: `tests/39-individual-agreements.test.ts`.
- **Service Agreement** (`server/service-agreement/contract.ts` + `pdf.ts`, `server/routes/service-agreement.ts`) — Livaware's "Service Agreement — Registered Nurse" (task 170) is the **first step of the Induction group** — it is **not** a blocking first step and does **not** lock the rest of the portal. It only becomes signable **once an admin has approved the nurse's compliance** (`gate.complianceApproved`, set via `POST /api/nurses/:id/compliance-approval`). The portal `draft`/`sign` routes enforce this with `requireComplianceApproved` (returns `403 { error: "compliance_not_approved" }` until approved); reading the contract is always allowed. **On-screen typed signature only — no upload.** The nurse reads the full 16-clause contract (read-to-end gate), types their full legal name, and completes identity fields (NMC PIN required, RCN/equivalent membership no. required, UTR/company number required, optional business name). Signing captures name/timestamp/IP/UA and renders a countersigned PDF stored as a `document`. **Reuses the declarations infrastructure — no table change**: `nurseDeclarations` with `declarationKey = "service_agreement"` (`SERVICE_AGREEMENT_KEY` in `contract.ts`); answers hold `{nmcPin, rcnMembershipNo, utrCompanyNumber, businessName}`. **Fully editable + versioned (re-sign on amend)**: the *entire* contract — title, preamble, every clause (text/items, add/remove/reorder), execution note, **Recovery Fee** (clause 12.1 token `{{RECOVERY_FEE}}`) and **countersignatory name/position** — is super-admin editable from `admin-settings.tsx` `ServiceAgreementConfigCard`. The full content lives in `appSettings` key `service_agreement_config` (defaults from `DEFAULT_SERVICE_AGREEMENT_CONFIG` at the **end** of `contract.ts` — defined after the seed constants to avoid a TDZ ReferenceError). **Every content change bumps the version**: `saveServiceAgreementConfig` compares a `contentSignature(...)` of the normalized content and increments `version` on any difference, returning `{config, versionBumped, previousVersion}`; the settings PUT audits `agreement_amended` (with previous/new version) when bumped, else `config_updated`. A version bump forces **all** previously-signed nurses to re-sign: `summarizeAgreement(latest, latestSubmitted, currentVersion)` derives `signed` (latest **submitted** version === current), `everSigned`, and `needsResign` (`everSigned && !signed`) from the latest *submitted* row (NOT `getLatest`, which can be a fresh re-sign draft and would mask the outstanding re-sign — see `getLatestSubmitted` in `declarations/storage.ts`). Portal/admin show a "re-sign required" banner; portal draft/sign create a new `nurseDeclarations` draft at the current version (no spurious 409 — 409 only when the *current* version is already submitted). PDF (`pdf.ts`) renders from the live config. Routes: portal `GET /api/portal/:token/service-agreement` (contract + state), `PUT /api/portal/:token/service-agreement/draft`, `POST /api/portal/:token/service-agreement/sign`; admin `GET /api/nurses/:id/service-agreement` (status + PDF + `currentVersion`/`needsResign`); settings `GET`/`PUT /api/admin/settings/service-agreement` (PUT super-admin, full content). Frontend: portal page `client/src/pages/portal/service-agreement.tsx` (tokenless `/portal/service-agreement` + legacy `/:token`), admin `client/src/components/admin/service-agreement-panel.tsx` (nurse-detail "Service Agreement" tab), `ServiceAgreementConfigCard` in `admin-settings.tsx`. `portal-shell.tsx buildPortalGroups` renders the Service Agreement as the first item of the **Induction** group (`onboard:service-agreement`): locked until `gate.complianceApproved`, then actionable, then "Signed" (flips back to actionable on a version bump). Audit module `service_agreement` (actions `agreement_signed`, `agreement_pdf_generated`, `agreement_viewed`, `agreement_amended`, `config_updated`). Tests: `tests/34-service-agreement.test.ts`.

Completion page `/portal/action` renders guided prompts via the shared `usePasteBlockedTextEntry` hook (`client/src/hooks/`) — extracted from the preboard assessment, which now consumes it too: paste/drop/shortcut blocking, paste-attempt + keystroke/burst telemetry, browser SpeechRecognition dictation. Witness statements require the honesty declaration server-side. The portal hub payload carries `assignedActions.outstanding`, driving a glowing "Action required" widget in `portal-shell.tsx` (bottom of desktop rail + mobile bar) and a To Do card on the hub. Submitted write-ups render in the admin panel with per-prompt answers, declaration status, and telemetry; super admin marks reviewed. Audit module `assigned_actions` (`assigned_action_assigned | email_sent | email_failed | submitted | reviewed`). Tests: `tests/41-assigned-actions.test.ts`.
- **HBC training sync** (`server/hbc/client.ts`, `server/hbc/service.ts`, `server/routes/hbc.ts`) — Integration with the **Healthier Business Group** compliance/training portal (https://dev.hbcompliance.co.uk) to sync mandatory CSTF training. Auth uses HB's V2 bearer-token flow (`POST /auth/token` with `{client_id, api_key}` → access token cached in-memory, lazy-refreshed 60s before expiry, auto re-auth on 401); candidate/training/certificate data read & written via HB's resource endpoints, which still also gate on `API-Key`/`API-Version` headers (sent alongside the bearer token). Full sync: pull course catalogue (`GET /training-list` → `hbcCourses`), push/create candidates (`POST /candidates`, form-urlencoded → `hbcCandidateLinks`, idempotent — 202 = already existed), pull per-nurse results (`GET /training-results/{ref}` → `hbcTrainingResults`, replace-on-sync), live candidate fetch, and combined certificates PDF download. Three admin-only mirror tables (`hbcCourses`, `hbcCandidateLinks` one-per-nurse, `hbcTrainingResults` unique on nurse+course) — **no portal surface by design**. Config via env (`HBC_CLIENT_ID`, `HBC_API_KEY`, `HBC_API_BASE_URL`, optional `HBC_API_VERSION`); `isHbcConfigured()` gates everything and routes return `503 hbc_not_configured` / `502 hbc_api_error` when HB is unreachable. Routes under `/api/admin/hbc/*` (status + reads = admin; test-connection, catalogue sync, candidate push, report sync = **super-admin**). Audit module `hbc` (actions `course_catalog_synced`, `candidate_created`/`candidate_matched`, `training_report_synced`). Super Admins drive it from the **HBC training sync** card on `/settings`.
- **Announcements** (`server/announcements.ts`, `server/routes/announcements.ts`) — Two one-off broadcast emails the Super Admin can fire from `/settings`: the **Platform update announcement** (heads-up that Skills Arcade / Policies / Availability / Invoicing are all live) and the **Platform launch & invoicing announcement** (introduces the portal, embeds the explainer video link when `PLATFORM_VIDEO_URL` is set, hard CTA to `https://onboard.livaware.co.uk`, informs nurses that all invoices must be submitted via the portal from 1 June 2026 because the legacy invoicing system is deprecated end of May 2026). Subject + HTML + plain-text body are stored in the **`emailTemplates`** table (key, subject, bodyHtml, bodyText, updatedBy/At) and seeded on first read. SAs edit them in `/settings` via `EmailTemplateEditor` (PUT `/api/admin/email-templates/:key`, super-admin only); preview/send always render through `renderAnnouncement(key, tokens)` with mustache-lite tokens (`{{NAME}}`, `{{PORTAL_URL}}`, `{{VIDEO_URL}}`) and conditional `{{#VIDEO_URL}}…{{/VIDEO_URL}}` blocks. Both share the same recipient filter (`!!email && !!fullName && currentStage !== "withdrawn"`), Microsoft Graph sender, per-recipient try/catch, and write per-recipient + summary audit rows under module `announcements` (actions `platform_update_announcement_sent`, `launch_announcement_sent`, `launch_announcement_run`, `email_template_updated`).

- **Mass email broadcast** (`server/routes/super-admin.ts`, task 186) — Super-admin-only compose-and-send tool at `/super-admin/mass-email`: roster-based recipient picker (search, select-all-filtered), subject + plain-text body (rendered into the branded envelope via `renderMassEmailHtml`, blank lines = paragraphs, all HTML escaped), up to 5 file attachments (dedicated in-memory multer — bytes are base64-inlined into the Graph messages and never written to the shared uploads dir, so they can't leak via `/api/uploads`; 3MB combined cap — Graph simple sendMail limit), in-dialog preview, and a post-send sent/failed/excluded summary. One Graph message per recipient via `sendMassEmailMessage` (`server/outlook.ts`); per-recipient failures are isolated per the bulk-loop convention. Persistence: `massEmails` (subject/body snapshot, attachment display metadata only — name/type/size, no stored file refs — counts, `excludedNoEmail`) + `massEmailRecipients` (per-nurse status/error). Nurses without an email are excluded and listed. Routes (all `requireSuperAdmin`): `GET /api/super-admin/mass-email/roster`, `POST …/preview`, `POST …/send` (multipart), `GET …/history`. Audit module `admin`: per-nurse `mass_email_sent`/`mass_email_failed` + summary `mass_email_broadcast`. Tests: `tests/38-mass-email.test.ts`.

## Authentication

- **Local**: `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `TEAM_USERNAME`/`TEAM_PASSWORD`, optional `SUPER_ADMIN_USERNAME`/`SUPER_ADMIN_PASSWORD` (checked first).
- **Microsoft 365 SSO** via MSAL (`server/msal-auth.ts`). Requires `AZURE_AD_TENANT_ID`, `AZURE_AD_CLIENT_ID`, `AZURE_AD_CLIENT_SECRET`. Redirect: `https://<domain>/api/auth/microsoft/callback`. If `SUPER_ADMIN_EMAIL` matches the SSO email, session is auto-promoted to `super_admin`.
- **Roles**: `admin` (read all, write candidates/nurses/portal/onboard), `team` (limited), `super_admin` (exclusive write to policies, settings, arcade imports, training-chase send/scan, nurse invites). Backend gate: `requireSuperAdmin` middleware. Frontend uses `<SuperAdminGate>` + `<SuperAdminViewOnlyBanner>`.
- **Nurse portal sign-in**: `/api/portal/auth/verify-code` returns a per-nurse `portalUrl` (resolved server-side from freshest non-expired token, or freshly-minted 30-day hub token). `/api/portal/auth/portal-url` re-resolves on every relevant client touchpoint.
